# ReviewOps

ReviewOps ist eine Custom GitHub Action (JavaScript). Sie startet bei neuen und aktualisierten Pull Requests, liest den Diff über die GitHub-API, schickt ihn an die OpenAI-API (Standardmodell `gpt-6-luna`) und postet das Feedback als Review mit Inline-Kommentaren am betroffenen Code.

Der Backlog liegt in den GitHub Issues dieses Repositories. Die Milestones „Phase 1“ bis „Phase 5“ geben die Reihenfolge vor. Jedes Issue nennt seine Tasks, seine Akzeptanzkriterien und in der Fußzeile seine Abhängigkeiten („Abhängig von: #n“).

## Arbeitsweise

- **Ein Issue nach dem anderen.** Der Maintainer gibt jede Phase und jedes Issue selbst frei. Ist ein Issue abgeschlossen, wird berichtet und gewartet, statt das nächste zu beginnen.
- **Kein Code auf Vorrat.** Gebaut wird, was das aktuelle Issue verlangt. Was ein späteres Issue liefert, bleibt dort.
- **Kleine, nachvollziehbare Schritte.** Vor jedem Schritt kurz sagen, was entsteht und wozu. Nie den gesamten Code auf einmal abliefern.
- **Ein Branch und ein Pull Request je Issue.** Der Branch heißt `issue-<nr>-<kurzname>`. `main` ändert sich nur über Pull Requests, damit ReviewOps seine eigenen Änderungen reviewt. Issue-Branches bleiben nach dem Merge stehen.
- **Sprache.** Antworten, Issues, Pull Requests und Commit-Messages sind deutsch. Bezeichner, Kommentare und Log-Ausgaben im Code sind englisch.

## Regeln für den Code

- Die Laufzeit ist Node.js 24, der Code besteht aus ES Modules (`import`/`export`). `@actions/core` liefert Inputs, Outputs und Logging, `@actions/github` den Octokit-Client, das offizielle `openai`-SDK den KI-Aufruf.
- Asynchroner Code nutzt `async/await`. Fehler werden mit `try/catch` abgefangen und enden in einer verständlichen Meldung über `core.setFailed()`.
- Secrets (GitHub-Token, OpenAI-Key) tauchen nirgends auf: nicht in Logs, Fehlermeldungen, Kommentaren oder Testdaten.
- Zero-Trust: Diff-Inhalte und Modellantworten sind nicht vertrauenswürdige Eingaben und werden geprüft, bevor sie etwas auslösen.
- `dist/` wird eingecheckt und muss zum Quellcode passen. Nach jeder Änderung unter `src/` neu bauen.
- Workflows binden fremde Actions über einen vollen Commit-SHA ein, die Version steht als Kommentar dahinter. Sie bekommen nur die Rechte, die sie brauchen.
- Module bekommen `core`, `context` und andere Runner-Objekte als Parameter, statt sie selbst zu importieren. Nur `src/main.js` verdrahtet die echten Module. So lassen sich alle Zweige mit `test/helpers/fake-core.js` und `test/helpers/fake-context.js` testen.
- `src/index.js` lädt `main.js` erst zur Laufzeit (`await import`) und meldet Fehler beim Laden über `core.setFailed()`. Manche Pakete arbeiten schon beim Laden, `@actions/github` liest zum Beispiel die Event-Datei ein. Deshalb gehört in `index.js` kein weiterer statischer Import außer `@actions/core`.
- Werte aus dem Event und aus dem PR (Titel, Branch-Namen, Dateinamen, Patches) stammen vom PR-Autor. Ins Log und in Fehlermeldungen kommen nur geprüfte Werte wie Nummer, SHA und Repository-Name. Dateinamen gehen vorher durch `printable()` aus `src/printable.js`, Patch-Inhalte werden nie geloggt.
- Zeilennummern berechnet die Action selbst: `parsePatch()` aus `src/diff/parse.js` liefert je Datei die Hunks und `commentableLines`, die Nummern der hinzugefügten Zeilen. Nur diese Zeilen sind Kommentarziele. Eine Zeilennummer aus einer Modellantwort gilt erst, wenn sie in `commentableLines` steht. `annotateDiff()` aus `src/diff/annotate.js` erzeugt den Diff-Text für das Modell und zeigt Nummern nur an hinzugefügten Zeilen.
- Dateien, die Secrets enthalten können, gehen nie ans Modell: `SENSITIVE_FILES` und `isSensitiveFile()` aus `src/exclude.js` (`.env*`, Schlüssel- und Zertifikatsdateien, `id_rsa*` und Verwandte, `.npmrc`, `.pypirc`, `.netrc`, `.git-credentials`, `credentials.json`, `secrets.*`, seit #110 auch `appsettings*.json`, `*.tfvars`, `*.tfvars.json`, `*.tfstate`, `*.tfstate.*`, `*.ppk`, `*.p8`, `*.ovpn`, `*.kdbx`, `.htpasswd`, `.pgpass`, `.dockercfg`, `.vault-token`). Die `appsettings*.json` stehen drauf, weil dort Connection-Strings und Schlüssel als JSON-Werte liegen, die kein Muster fände; ein Pull Request, der sie ändert, zeigt die Warnung zu möglichen Secrets. Die Liste ist fest, wird vor allen anderen Filtern geprüft und lässt sich über keinen Input ändern. Geprüft werden der neue und bei Umbenennungen auch der alte Name (`previousPath` aus `src/github/files.js`). Solche Dateien stehen mit Grund im Log und in einer Warnung. Erweiterungen der Liste brauchen ein Issue.
- Was wie ein Secret aussieht, maskiert `maskSecrets()` aus `src/secrets.js` direkt nach dem Parsen zu `[REDACTED SECRET]` (`SECRET_PLACEHOLDER`): Private-Key-Blöcke und feste Token-Formate (GitHub, OpenAI, seit #110 Anthropic mit zweistelliger Version nach `sk-ant-` (sonst träfe es CSS-Klassen), GitLab mit allen Präfixen der Tabelle der GitLab-Doku, npm `npm_` plus 36 Zeichen, PyPI `pypi-AgEIcHlwaS5vcmc`, Docker Hub `dckr_pat_` und `dckr_oat_`, Hugging Face `hf_` plus mindestens 34 Zeichen, AWS-Access-Key-IDs, Slack, Stripe-Live, Google-API). Jedes neue Format braucht einen Beleg (Doku des Anbieters oder Eintrag in GitHubs Liste der Muster für Secret Scanning), die Längen sind Untergrenzen, und jede Wiederholung steht allein. Connection-Strings außerhalb von `appsettings*.json` bleiben bewusst unmaskiert (ein Test hält das fest, `SECURITY.md` nennt es); `test/eval-cases.test.js` hält fest, dass kein Muster und kein Eintrag einen Referenz-Diff ändert. Ein Schlüsselblock ohne END im Hunk setzt sich im nächsten Hunk fort, solange dessen Zeilen wie der Rest eines Schlüssels aussehen; zwei oder mehr aufeinanderfolgende Zeilen wie ein PEM-Körper (nur Base64, 60 bis 76 Zeichen) werden auch ohne BEGIN und END maskiert, weil ein PR mit einer geänderten Zeile mitten im Schlüssel nur Körperzeilen zeigt. Allgemeine Muster wie `password = "…"` gehören absichtlich nicht dazu, sie träfen Tests und Beispiele. Die regulären Ausdrücke laufen linear, auch bei sehr langen Zeilen vom PR-Autor. Zeilenzahl und Zeilennummern bleiben gleich, alle Zeilenarten werden maskiert, das Budget zählt den maskierten Text. Ins Log kommen nur Anzahl und Dateinamen, nie ein gefundener Wert. Die Auswertung maskiert genauso.
- Welche Dateien nicht reviewt werden, entscheidet `createExcludeFilter()` aus `src/exclude.js`: die Standardliste `DEFAULT_EXCLUDES` plus die Muster aus dem Input `exclude`. Der Abgleich läuft über `picomatch` mit festen Optionen. Eigene Muster sind begrenzt (höchstens zwei `*` und zwei `**` im ganzen Muster, 50 Muster, keine Negation, keine Klammern), weil Dateinamen vom PR-Autor stammen und ein Muster mit vielen Platzhaltern sonst minutenlang rechnet. Gezählt wird über das ganze Muster, weil sich Sterne in mehreren Verzeichnissen multiplizieren. Ein Verzeichnismuster wie `dist/**` meint die Dateien darunter, nicht eine Datei mit dem Namen `dist`. Ein ungültiges Muster lässt den Lauf vor dem ersten API-Aufruf scheitern.
- Der Ablauf in `run()` ist: abrufen, Verlauf lesen, filtern, parsen, Bereich anwenden, begrenzen, bündeln, senden. Bleibt nach dem Begrenzen keine Datei, endet der Lauf grün mit einer `core.notice()`. Alles, was Geld kostet oder etwas postet (KI-Aufruf, Review), steht hinter dieser Stelle.
- Die Größe eines Pull Requests begrenzen `max-files` (Standard 50) und `max-diff-chars` (Standard 200000): `parseLimits()` und `applyLimits()` aus `src/limits.js`. `parseLimits()` liest auch `max-comments`. Gezählt wird je Datei, was sie im Aufruf kostet (#108): ihr Block `<file path="…">` bis `</file>` mit annotiertem Diff plus ein Trenner (`budgetCostOf()` aus `src/ai/batch.js`, übergeben als `request.costOf` an `applyLimits()`; ohne `costOf` zählt die Länge des annotierten Diffs). So bleiben alle User-Prompts zusammen unter `max-diff-chars`, und die Pfade zählen mit. Daraus folgt für jeden Pull Request: höchstens `maxRequestsFor(maxDiffChars)` = `2 · ⌈max-diff-chars / 50000⌉ − 1` Aufrufe, mit den Standardwerten 7 (zwei aufeinanderfolgende Aufrufe wiegen zusammen mehr als `MAX_REQUEST_CHARS`; Begründung am Code). `run()` prüft das nach `planBatches()` als Invariante vor dem ersten Aufruf (ein Defekt, `planBatches` ist dafür als Parameter injizierbar). Eine feste Obergrenze gibt es nicht, damit ein höheres `max-diff-chars` seine Wirkung behält. Gewählt wird in der Reihenfolge von GitHub. Eine Datei, die nicht mehr ins Restbudget passt, entfällt allein, spätere kleinere kommen noch hinein. Ausgelassene Dateien stehen mit Grund im Log und in einer Warnung, ein ungültiger Wert scheitert vor dem ersten API-Aufruf. Die Standardwerte stehen in `action.yml` und in `src/limits.js`, ein Test hält sie gleich. Wer den Text für das Modell braucht, nimmt `annotated` der gewählten Datei, statt `annotateDiff()` erneut aufzurufen.
- Den Aufruf des Modells kapselt `createAiClient()` aus `src/ai/client.js` (`complete({ system, user })`), das offizielle `openai`-SDK über die Chat-Completions-Schnittstelle. Die SDK-Optionen sind fest: Adresse `https://api.openai.com/v1`, keine Organisation, kein Projekt, SDK-Logging aus. Ohne sie übernähme das SDK `OPENAI_BASE_URL`, `OPENAI_ORG_ID` und `OPENAI_LOG` aus der Umgebung und schickte Key und Code dorthin. Timeout 120 Sekunden je Versuch, zwei Wiederholungen durch das SDK. Mehrere Aufrufe gleichzeitig sind erlaubt. Der API-Key muss aus sichtbaren ASCII-Zeichen bestehen (`assertInputs()`), sonst scheitert das SDK mit einer Meldung über einen Header.
- Prompt und Antwort des Modells enthalten Code aus dem Diff und werden nie geloggt, auch nicht im Debug-Log. Ins Log kommen nur Kennzahlen: Modell, Token-Verbrauch, Anfrage-ID.
- Fehler des Clients sind `AiError` mit eigenem Text und einem Feld `kind`. Der Text von OpenAI wird nie übernommen und nicht als `cause` angehängt: OpenAI nennt in der Meldung zu einem ungültigen Key dessen Anfang und Ende, und der Schwärzer kennt nur den ganzen Key. Werte aus der Antwort (Code, Typ, Anfrage-ID, Modellname) erscheinen im Log nur, wenn sie wie ein Bezeichner aussehen, die Token-Zahlen nur, wenn alle drei ganze Zahlen ab 0 sind. Nach `auth`, `permission`, `model` und `quota` lohnt kein weiterer Aufruf: `isFatal()` aus `src/ai/error.js`.
- Der Modellname kommt über `parseModel()` aus `src/ai/model.js`. Die Datei importiert das SDK nicht.
- Das Antwortformat des Modells steht an genau einer Stelle: `src/ai/schema.js` (`REVIEW_SCHEMA`, `REVIEW_FORMAT`, `MAX_OUTPUT_TOKENS`, `parseReview()`). Die Anfrage sendet es als Structured Output (`json_schema`, `strict: true`, `max_completion_tokens: 4096`), `parseReview()` prüft die Antwort mit `src/ai/json-schema.js` gegen dasselbe Objekt, auch wenn der Strict-Modus es schon erzwingt. Das Schema hält die Regeln des Strict-Modus ein (alle Felder in `required`, `additionalProperties: false`, keine Längen- und Mengengrenzen); `json-schema.js` kennt nur diesen Teil von JSON Schema und lehnt jedes andere Schlüsselwort ab. Die Tabelle in `docs/response-format.md` und das Schema bleiben gleich, ein Test prüft das. Eine abgeschnittene (`truncated`), gefilterte (`filtered`), abgelehnte (`refusal`) oder nicht passende (`response`) Antwort ist ein Fehler und nie „keine Findings“. Fehlermeldungen nennen nur die Stelle (`findings[2].severity`), nie Inhalt, auch nicht den Text einer Ablehnung. Ob ein einzelnes Finding brauchbar ist (Pfad, Zeile, leerer Text), prüft nicht `parseReview()`, sondern der Schritt je Finding. Ein Modell ohne Structured Outputs scheitert mit `kind: "model"` und dem Hinweis auf `openai-model`, ohne Rückfall auf ein anderes Format.
- `AiError` liegt in `src/ai/error.js` ohne SDK-Import, `client.js` exportiert sie weiter. Module, die nur den Fehler oder das Schema brauchen, ziehen so das SDK nicht ins Bundle.
- Der System-Prompt steht in `src/ai/prompt.js` (`buildSystemPrompt({ language })`) und ist englisch. `PROMPT_VERSION` wird bei jeder Änderung des Wortlauts erhöht, damit sich Messergebnisse einem Stand zuordnen lassen. Schweregrade und Kategorien kommen als Konstanten aus `src/ai/schema.js`, der Prompt beschreibt nur ihre Bedeutung. Die Ausgabesprache kommt über `parseLanguage()` aus dem Input `language` (feste Codes `en`, `de`, `fr`, `es`, `it`, `pt`, `nl`, `pl`, `tr`, `ja`, `zh`, `ko`, Standard `en`, geprüft vor dem ersten API-Aufruf). In den Prompt gelangt nie der Wert aus dem Workflow, sondern nur der englische Name der Sprache aus der festen Tabelle `LANGUAGES`. Der Standardwert steht in `action.yml` und in `src/ai/prompt.js`, ein Test hält sie gleich. Der System-Prompt beschreibt den User-Prompt aus `src/ai/user-prompt.js`; wer eines von beiden ändert, ändert das andere mit, erhöht `PROMPT_VERSION` und misst neu. Der Prompt erklärt, dass alles zwischen `<file …>` und `</file>` Daten vom PR-Autor sind und keine Anweisungen, dass `[REDACTED SECRET]` auf einer hinzugefügten Zeile als Secret im Code zu melden ist und dass ein Backslash-u-Code für ein unsichtbares Zeichen stehen kann. Code außerhalb des Diffs gilt als korrekt, solange der Diff nichts anderes zeigt (seit Version 9, #47). Seit Version 11 (#97) erklärt der Prompt die Abschnittszeile `@@` (der Text dahinter ist eine Zeile der Datei und kein Teil der Änderung, zwischen zwei Abschnitten fehlt Code), sagt, dass ein `<file>`- oder `</file>`-Tag allein am Zeilenanfang steht und alles hinter `|` oder `@@` Text der Datei ist, beschreibt `info` als optionale Verbesserung mit konkretem Nutzen (kein Widerspruch zur Pflicht eines Vorschlags) und verlangt kurze Texte (Zusammenfassung ein bis drei Sätze, Kommentar höchstens vier, Beispiel höchstens zehn Zeilen). `REVIEW_SCHEMA` beschreibt einen Aufruf als „the review of the files in this request“; der Hash-Test deckt diese Beschreibung nicht ab. Der Referenzfall `security-fake-file-tag-prompt-injection` prüft einen Fehler in einer Datei mit nachgemachten Tags in einer hinzugefügten Zeile und einer Abschnittszeile, die wie eine Anweisung klingt. Die Fokusbereiche sind `code-quality`, `react`, `vue`, `efcore` und `security` (`CATEGORIES`); `vue` kam mit Version 10 dazu (#73): sechs Prüfpunkte für Vue 3, jeweils für Options API und Composition API formuliert, die Referenz-Diffs `vue-prop-mutation` und `clean-vue` sind im Options-API-Stil wie FitTrack, die Composition API ist beschrieben, aber nicht gemessen. Bis #74 stehen die Vue-Prüfpunkte in jedem Prompt.
- Den User-Prompt baut `buildUserPrompt({ files })` aus `src/ai/user-prompt.js`: je Datei `<file path="…">` mit dem annotierten Diff und `</file>`. Der Titel des Pull Requests gehört absichtlich nicht dazu: Mit ihm meldete `gpt-4.1` beim sauberen Referenz-Diff `clean-react` in 6 von 6 Durchgängen einen Fehlalarm, ohne ihn in 0 von 3 (#14). Wer ihn wieder aufnimmt, misst vorher neu. Ein Pfad steht unverändert im Attribut, damit das Modell ihn genau so zurückgibt; eine Datei, deren Pfad `"`, `<`, `>` oder Steuer- und Zeilentrennzeichen enthält (`isUsablePath()`), entfällt schon beim Filtern mit Grund. Jede Zeile des annotierten Diffs beginnt mit der Nummernspalte, ein Tag steht also nie am Zeilenanfang. `annotateDiff()` zeigt Steuerzeichen außer Tab, unsichtbare Formatzeichen und Zeilen- und Absatztrenner als Backslash-u-Code (für U+2028 also Backslash, `u`, `2028`), auch in der Abschnittszeile `@@ …`. So kann keine Codezeile wie eine eigene nummerierte Zeile aussehen, und Bidi-Steuerzeichen bleiben sichtbar.
- Ein Aufruf des Modells hält höchstens `MAX_REQUEST_CHARS` (50000) Zeichen User-Prompt (`src/ai/batch.js`). `planBatches()` füllt die Aufrufe in der Reihenfolge von GitHub, bis die nächste Datei nicht mehr passt; eine Datei wird nie geteilt. Eine Datei, die allein größer ist als ein Aufruf, entfällt schon in `applyLimits()` (`tooLarge`) mit Grund und Warnung und zählt weder für `max-files` noch für `max-diff-chars`.
- `reviewInBatches()` aus `src/review.js` schickt die Aufrufe mit höchstens `MAX_PARALLEL_REQUESTS` (4) gleichzeitig, prüft jede Antwort mit `parseReview()` und liefert je erfolgreichem Aufruf dessen Dateien, Zusammenfassung und Findings (`reviews: { files, summary, findings }[]`) in der Reihenfolge der Aufrufe. Ein fehlgeschlagener Aufruf (`AiError`) nimmt die anderen nicht mit; nach einem fatalen Fehler startet kein neuer, und die nicht gesendeten zählen als fehlgeschlagen. Alles andere als ein `AiError` ist ein Defekt und lässt den Lauf scheitern. In `run()` gilt: Schlägt ein Teil fehl, endet der Lauf grün mit einer Warnung (Zahl der Aufrufe und Dateien, Meldungen des Clients) und je einer Zeile „Not reviewed …“; schlagen alle fehl, scheitert er mit der Meldung des ersten Fehlers. Ins Log kommen nur Zahlen: Dateien und Aufrufe, Findings je Schweregrad.
- Jeder Text der Modellantwort wird in `reviewInBatches()` direkt nach `parseReview()` durch `boundReview()` aus `src/ai/answer-limits.js` begrenzt und bereinigt (`TEXT_LIMITS`: Titel 150, Kommentar 1500, Vorschlag 1500, Zusammenfassung 1000 Zeichen, nach Zeichen gezählt, gekürzt mit `…`; Steuerzeichen, unsichtbare Formatzeichen und leer aussehende Zeichen wie das Braille-Leerzeichen entfallen, der Titel wird einzeilig). Alles dahinter sieht nur diese Texte. Das Ergebnis nennt die Zahl der gekürzten Texte als `shortened`. Markdown entschärft erst das Review selbst.
- Fehlt der API-Key, entscheidet `explainMissingSecret()` aus `src/github/context.js`: Bei einem Fork-PR oder einem von Dependabot ausgelösten Lauf (`context.actor`) hat GitHub keine Secrets bereitgestellt, und `run()` endet vor jeder Anfrage grün mit einer `core.notice()`. Bei jedem anderen PR bleibt es ein Fehler. Der Text der Meldung enthält nichts aus dem Event.
- `SECURITY.md` beschreibt Datenfluss, Rechte, Events, Umgang mit der Antwort und den Meldeweg. `test/security-doc.test.js` hält Sperrliste, Rechte und Textgrenzen darin mit dem Code gleich und sichert `src/`: kein `eval`, keine Funktionen aus Text, kein `child_process`, kein eigener Netzaufruf außer in `src/insights/send.js` (#76), nur die vier erlaubten Pakete (`@actions/core`, `@actions/github`, `openai`, `picomatch`) und das Node-Modul `node:crypto` für die Fingerprints und die `deliveryId`, ein neues Paket ist eine Entscheidung des Maintainers. Wer das Verhalten der Action ändert, ändert `SECURITY.md` mit.
- Welche Findings das Review zeigt, entscheidet `selectFindings()` aus `src/findings.js`, eine reine Funktion, je Finding gegen die Dateien des eigenen Aufrufs: Ein leerer Titel, Kommentar oder Vorschlag (nur Leer- oder Formatzeichen) und ein Pfad, der nicht exakt zu einer Datei dieses Aufrufs gehört, fallen weg; ein unbekannter Pfad kommt auch nicht in den Review-Text, weil das Modell die Datei nie gesehen hat. Von Findings mit gleichem Pfad, gleicher Zeile und gleichem Titel (ohne Groß- und Kleinschreibung und überzähligen Leerraum) bleibt das schwerste. Danach wird stabil nach Schweregrad sortiert und auf `max-comments` gekürzt (Standard 10, in `action.yml` und `src/limits.js`, gelesen von `parseLimits()`). Die Grenze gilt für alle gezeigten Findings, der Rest entfällt und wird gezählt. Erst dann wird aufgeteilt: Steht die Zeile in `commentableLines`, wird das Finding ein Inline-Kommentar (`inline`), sonst steht es im Review-Text (`unplaced`). Ins Log kommt eine Zeile mit den Zahlen jedes Schritts, nie ein Pfad oder Text eines Findings. Die Tabelle in `docs/response-format.md` beschreibt die Schritte.
- Erneute Läufe auf demselben PR (#18): `readHistory()` aus `src/github/history.js` liest mit `listReviews` und `listReviewComments` (paginiert) die eigenen Reviews und Kommentare. Eigen ist, was mit `REVIEW_MARKER` beginnt **und** von dem Konto stammt, dessen Token der Lauf nutzt (#106): `readOwnAccountId()` aus `src/github/identity.js` fragt es einmal je Lauf über GraphQL `viewer { databaseId }`, `readHistory()` vergleicht `user.id` mit dieser ID (nicht Login, nicht Typ: GraphQL schreibt den Bot als `github-actions` ohne `[bot]`, eine ID bleibt bei Umbenennung gleich; gültig nur als positive ganze Zahl). Gefragt wird nur, wenn mindestens ein Review oder Kommentar mit dem Marker beginnt, ein erster Lauf macht keinen zusätzlichen Aufruf. Das deckt `GITHUB_TOKEN`, eine eigene GitHub App und einen PAT ab. Scheitert die Abfrage oder ist die Antwort unbrauchbar (`IdentityUnavailableError`, Texte nie aus der Antwort), scheitert ein Lauf mit Review und auch der übersprungene vor dem KI-Aufruf; beim geschlossenen Pull Request ist es eine Warnung ohne Statusbericht (`isReadingError()`). Alles andere wird nie gelesen und nie verändert (die Action schreibt nur das eine neue Review). Grenzen (`SECURITY.md`): Alle Workflows mit dem `GITHUB_TOKEN` teilen `github-actions[bot]`; nach einem Wechsel des Tokens gehören frühere Reviews einem anderen Konto; der Inhaber eines PAT kann den Marker selbst setzen. Die Tests nehmen `OWN_ACCOUNT` aus `test/helpers/github-api.js` (ID 41898282); `createFakeOctokit()` und `startGitHubApi()` beantworten die Abfrage (Option `viewer`, Aufzeichnung in `viewerQueries`, getrennt von `queries`). Der `commit_id` des neuesten eigenen Reviews ist der Ausgangspunkt (kein SHA im Marker, weil GitHub ihn selbst hält und er sich nicht fälschen lässt). `compareCommitsWithBasehead(<commit_id>...<Head>)` liefert die neuen Zeilen; neu ist eine Zeile, die im Vergleich **und** im PR-Diff hinzugefügt ist (`scopeDiffs()`). Dateien ohne neue Zeile gehen nicht noch einmal ans Modell, zählen nur im Log und stehen nicht unter „nicht reviewt“; die anderen gehen mit ihrem ganzen PR-Diff. Ein vollständiges Review folgt bei keinem eigenen Review, bei Vergleich `404`, `diverged`, `behind` und bei unvollständigem Vergleich (3000 Dateien); im Zweifel wird mehr geprüft, nie weniger. Ist der Head schon geprüft oder hat keine Datei eine neue Zeile, endet der Lauf grün mit einer `core.notice()` und ohne KI-Aufruf. Fehler beim Lesen (außer `404` beim Vergleich) scheitern über `describeApiError()` vor dem KI-Aufruf. Jeder Inline-Kommentar trägt in der zweiten Zeile `<!-- reviewops-fingerprint: <16 hex> -->` (`fingerprintLine()`; `lineFingerprint()` aus `src/fingerprint.js`: SHA-256 über Pfad, Zeilentext und Text der Zeile davor im Hunk aus dem maskierten Diff, Leerraum zusammengefasst, die ersten 16 Hex-Zeichen; `lineFingerprintsOf()` liefert sie für alle Zeilen mit Nummer, auch Kontextzeilen). Seit #107 steht in der Zeile eines Inline-Kommentars auch der Text-Fingerprint (`textFingerprint()`, `textFingerprintsOf()`: SHA-256 nur über den Zeilentext, Leerraum zusammengefasst, ohne Pfad und ohne Vorgänger; `null` für Zeilen ohne Buchstaben und Ziffern wie `}`), siehe unten bei den offenen Findings. Gelesen werden nur die Zeilen direkt unter dem Marker (`readHead()`, `
` oder `
`), mit einem strengen regulären Ausdruck, nie der Text weiter unten, und nur aus eigenen Kommentaren und Reviews, auch aus veralteten und aufgelösten. Findings im Review-Text (`unplaced`) tragen ihren Fingerprint im Kopf des Review-Textes. Ein Review eines Laufs, der etwas ausließ, das ein neuer Lauf nachholen kann (fehlgeschlagener Aufruf, Findings über `max-comments`; Dateien über einem Limit oder mit unlesbarem Diff nicht, ein voller Lauf ließe sie wieder aus), trägt unter dem Marker `<!-- reviewops-incomplete -->` (`INCOMPLETE_LINE`) und ist nie ein Ausgangspunkt. `selectFindings()` kennt dafür `newLines` (ein `unplaced`-Finding zählt, wenn seine Datei eine neue Zeile hat und der Diff seine Zeile zeigt) und `known` und zählt `notNew` und `known` vor dem Kürzen auf `max-comments`; `fingerprints` laufen parallel zu `inline`. Der Review-Text nennt im inkrementellen Modus „Reviewed the changes since `<sha7>`“. Ins Log kommen nur Zahlen und der geprüfte SHA, nie ein Kommentar oder Fingerprint. Grenzen (in `SECURITY.md`): Ein Lauf ohne Findings postet nichts und lässt den Ausgangspunkt stehen; mit einem PAT erkennt sich die Action wieder, solange der Token nicht wechselt.
- Ergebnis eines Laufs (#19): Jeder Lauf schreibt eine Job Summary (`buildSummary()` aus `src/summary.js`): Status, reviewte, übersprungene (höchstens 50 mit Namen als Inline-Code) und schon geprüfte Dateien, offene Findings je Schweregrad, Token-Verbrauch (`reviewInBatches()` liefert `usage`, Aufrufe ohne Zahl zählen als `withoutCount`) und den Link zum Review. Text des Modells steht nie in der Summary; Status und Fehlermeldung gehen durch `plainText()`. `run()` sammelt alles in `report` und schreibt Summary und Outputs (`setOutputs()` aus `src/outputs.js`: `findings-count`, `critical-count`, `review-url`) in `finally`; ein Fehler beim Schreiben wird zur Warnung. Outputs gibt es an jedem regulären Ende (vor dem Parsen `0`, `0`, leer), nach einem Fehler keine. Offen ist ein Finding dieses Laufs nach Schritt 5 von `selectFindings()` (vor dem Kürzen, `counts`) oder ein früherer eigener Inline-Kommentar, dessen Fingerprint noch eine hinzugefügte Zeile des PR trägt (`currentEarlierFindings()`) und dessen Thread nicht aufgelöst ist (`countOpenFindings()` aus `src/open-findings.js`, je Zeile, wie sie jetzt ist, einmal mit dem schwersten Schweregrad). Dafür trägt die Fingerprint-Zeile eines Inline-Kommentars den Schweregrad und den Text-Fingerprint (`<!-- reviewops-fingerprint: <16 hex> severity: <severity> text: <16 hex> -->`, `fingerprintLine(fingerprint, severity, text)`, `text` nur zusammen mit `severity`, nie im Kopf eines Review-Textes); `readHistory()` liefert sie als `earlierFindings` mit Kommentar-ID, `path` und `textFingerprint` (`null` bei Kommentaren von vor #107; `inlineComments` trägt ihn auch). Die eine Regel „ist das frühere Finding noch aktuell“ steht in `assessComments()` aus `src/open-findings.js` (#107), genutzt von der Zählung (`openEarlierFindings()`, `currentEarlierFindings()`), von `known` für `selectFindings()` und von `buildStatusPayload()`; der Reihe nach: Diff der Datei nicht verfügbar (`unknownPathsOf()`, oder abgeschnittene Liste und Datei nicht geparst) = `unknown`, zählt als offen; Fingerprint unter den hinzugefügten Zeilen = unverändert; Text-Fingerprint steht als hinzugefügte Zeile der eigenen Datei (hat die Datei keinen geparsten Diff mehr, in allen Dateien) = unverändert; sonst geändert. Trifft der Text genau eine Zeile, gilt deren heutiger Fingerprint als Schlüssel und als schon kommentiert (`commented`, damit ein vollständiger Lauf es nicht noch einmal postet), bei mehreren nicht. Die Text-Fingerprints der Zeilen werden nur berechnet, wenn ein Kommentar Schritt 3 erreicht, und gehen nie an Insights. Grenzen (`SECURITY.md`): derselbe Text ein zweites Mal hält ein Finding offen, ein vollständiger Lauf kann es bei mehreren Treffern doppelt posten, gelöschte Datei mit gleichlautender Zeile anderswo, Kommentare von vor #107 und Zeilen ohne Buchstaben und Ziffern folgen der alten Regel; der Ausweg ist der aufgelöste Thread. Ins Log kommt die Zahl der Findings, die ohne Diff als offen zählen. Aufgelöste Threads liest `readResolvedComments()` aus `src/github/threads.js` über `octokit.graphql` (REST kennt den Status nicht), nur wenn ein früherer Befund noch aktuell ist, und vor dem KI-Aufruf. Antwortet GitHub nicht, wirft es `ThreadsUnavailableError` (Text über `describeApiError()`, GraphQL-Fehlertexte werden nicht übernommen); ohne `fail-on` läuft `run()` dann mit Warnung weiter und zählt alle früheren Befunde als offen, mit `fail-on` scheitert der Lauf, ein Defekt immer. Der Input `fail-on` (`parseFailOn()` aus `src/fail-on.js`, `none`, `critical`, `major`, Standard `none` in `action.yml` und im Code, ein Test hält sie gleich) lässt den Step an jedem regulären Ende per `core.setFailed()` scheitern, nach dem Posten und auch, wenn nichts Neues zu prüfen war: Ein Re-Run macht einen roten Check nicht grün. Findings im Review-Text und Kommentare ohne Schweregrad zählen nur im Lauf, der sie fand. `reviewops.yml` gibt die Outputs in einem Folge-Step über Umgebungsvariablen aus, nie als Ausdruck im Befehl. `fail-on` ist eine Erinnerung, bewusst mit offenen Findings umzugehen (Code ändern oder Thread auflösen), und kein Schutz gegen einen Autor, der den Check umgehen will (#109): Die Grenzen stehen in `SECURITY.md` in einem Abschnitt „What fail-on is, and what it is not“ (README und `action.yml` verweisen darauf, `test/security-doc.test.js` hält Kernsatz und Verweise fest). Wer die Zählung oder die Wege dorthin ändert (Limits, Ausschlüsse, Marker, Threads), zieht diesen Abschnitt nach.

## Logging

Ausgaben laufen ausschließlich über `@actions/core`; `console.*` ist unter `src/` per ESLint verboten.

- `core.info()` meldet den Fortschritt, eine Zeile je Schritt.
- `core.notice()` ist für Hinweise an den Nutzer der Action, etwa einen übersprungenen Lauf.
- `core.warning()` meldet, was übersprungen oder nur teilweise erledigt wurde, ohne dass der Lauf scheitert.
- `core.debug()` nimmt Details und Stacktraces auf. Sie erscheinen nur bei eingeschaltetem Debug-Logging.
- `core.setFailed()` wird nur in `run()` aufgerufen, mit einer Meldung, die sagt, was zu tun ist.
- Nie ausgegeben werden Payloads, Header und ganze Fehlerobjekte. Fehlertexte gehen vor der Ausgabe durch den Schwärzer aus `src/redact.js`.

## Ablauf je Issue

| Schritt | Skill | Ergebnis |
|---|---|---|
| Standort klären | `/orientation` | Projektstand und nächstes umsetzbares Issue |
| Issue schärfen | `/drilling <nr>` | geklärte Entscheidungen und ein abgestimmter Plan |
| Umsetzen | `/implement <nr>` | Code, Tests und ein Nachweis je Akzeptanzkriterium |
| Prüfen | `/review-issue <nr>` | Befunde und ein Urteil |
| Abschließen | `/ship <nr>` | Commit und Pull Request, nach dem Merge ein abgehaktes Issue |
| Fehler suchen | `/diagnose` | Ursache eines fehlgeschlagenen Workflow-Laufs |

Fehlt beim Aufruf die Issue-Nummer, ergibt sie sich aus dem Branch-Namen. Auf `main` ist das nächste umsetzbare Issue gemeint: das offene Issue mit der kleinsten Nummer im frühesten Milestone mit offenen Issues, dessen Abhängigkeiten alle geschlossen sind. Der Maintainer bestätigt es, bevor gearbeitet wird.

## Befehle

- `npm ci` installiert die Abhängigkeiten exakt nach `package-lock.json`.
- `npm test` führt die Tests mit dem eingebauten Test-Runner aus (`node --test`). Testdateien liegen unter `test/` und heißen `*.test.js`.
- `npm run lint` prüft den Code mit ESLint und die Formatierung mit Prettier.
- `npm run format` formatiert den Code mit Prettier (Standardstil, Markdown ausgenommen).
- `npm run eval` wertet den Prompt gegen die echte OpenAI-API aus (`OPENAI_API_KEY` in der Umgebung, optional `EVAL_MODEL` und `EVAL_LANGUAGE`): jeder Referenz-Diff dreimal, ohne `EVAL_LANGUAGE` auf Englisch, Ergebnis als Tabelle. `EVAL_LANGUAGE` prüft `parseLanguage()` wie den Input `language` der Action; die Schwellen gelten in jeder Sprache, weil Schweregrad, Kategorie, Pfad und Zeile englisch bleiben. Gemessen wird ohne Angabe mit dem Standardmodell der Action (`DEFAULT_MODEL`, #93); `EVAL_MODEL` und der Input `model` von `eval.yml` wählen ein anderes. Zuvor galt `gpt-4.1` als Referenzmodell (`REFERENCE_MODEL`, entfallen). Bekannte Grenze bei `gpt-4.1`: Der Fehlalarm bei `clean-react` kam mit Prompt-Version 9 und 10 immer wieder zurück (Version 9 am 08.10. 2 von 3 Durchgängen ohne Fehlalarm, Version 10 mit allen Bereichen 4 von 9, mit den passenden Bereichen 0 von 9, #74), in 12 von 14 Fällen als Annahme, `item.id` sei als `key` womöglich nicht eindeutig oder stabil, also über Daten außerhalb des Diffs; `gpt-6-luna` zeigte ihn in 18 von 18 Durchgängen nicht. Der Check `eval` ist mit `gpt-4.1` deshalb nicht zuverlässig grün, mit dem Standardmodell schon. Mit `gpt-6-luna` und `gpt-6.1-sol` erreicht der Prompt (Version 9) alle Schwellen, mit `gpt-4o-mini` nicht (`react-missing-dependency` nur 1 von 3, #41). Mit Version 10 (Vue, #73) erreichte `gpt-6-luna` alle Schwellen, `vue-prop-mutation` und `clean-vue` in jedem Durchgang (3 von 3); für `gpt-4.1` siehe die bekannte Grenze oben. Ein Lauf kostet 30 Aufrufe mit rund 61500 Eingabe- und 4000 Ausgabe-Tokens bei `gpt-4.1`, rund 7200 Ausgabe-Tokens bei `gpt-6-luna`. Die Schwellen: ein Fehlerfall wird in 3 von 3 Läufen gefunden, ein sauberer Diff bleibt in mindestens 2 von 3 Läufen ohne Finding ab `major` (das weicht vom Wortlaut „3 von 3“ in #12 ab), ungültige Findings sind nie erlaubt, und ein Lauf mit Fehler wird nie toleriert. Begründung der Schwellen (#47): Die Fehlerfälle fand `gpt-4.1` in den Läufen aus #12 jedes Mal (3 von 3), deshalb gilt dort 3 von 3. Geschwankt haben nur die sauberen Diffs: Dasselbe Modell mit demselben Prompt war in #12 einmal grün und einmal rot. Der wiederkehrende Fehlalarm bei `clean-react` kam vom PR-Titel im Prompt (6 von 6 Durchgängen mit Titel, 0 von 3 ohne, #14). Mit Prompt-Version 8 waren in #47 sechs Läufe auf unverändertem Stand fünfmal grün und einmal rot: Die Fehlerfälle wurden immer gefunden, `clean-csharp` blieb immer sauber, `clean-react` hatte 3 Fehlalarme in 18 Durchgängen, die alle über Code außerhalb des Diffs rieten (ob eine Prop stabil ist, ob ein `AbortSignal` beachtet wird); ein Lauf auf Deutsch erfüllte alle Schwellen. Version 9 macht die Regel „nicht raten“ deshalb an solchen Beispielen konkret; danach waren fünf Läufe auf unverändertem Stand alle grün, mit jedem Fall in jedem Lauf bei 3 von 3, auch `clean-react` (15 von 15), und ebenso der Lauf auf Deutsch. Die Toleranz von einem Ausreißer bleibt, damit ein einzelner Fehlalarm bei unverändertem Prompt den Check nicht rot färbt. Mehr Läufe je Fall kosten zwei Drittel mehr und drücken auf das Token-Limit von `gpt-4.1`; ein automatischer Sprachtest brächte neue Streuung. Ob das Feedback in der gewählten Sprache kommt, belegt ein Lauf von Hand mit `language` (#47). Er endet mit Fehler, wenn eine Schwelle verfehlt wird oder der Key fehlt. Nur bei einem Pull Request ohne Secrets (Fork) endet er ohne Key mit einem Hinweis. Er gehört nicht zu `npm test`; `.github/workflows/eval.yml` startet ihn bei Änderungen an `src/ai/`, `eval/` (ohne `eval/compare/`) und am Workflow sowie von Hand, dann mit den Inputs `model` und `language`. Läufe von Hand auf demselben Branch teilen sich eine Concurrency-Gruppe und brechen einander ab; für Messreihen werden sie nacheinander gestartet. Der Pfadfilter betrachtet den ganzen Pull Request, nicht nur den letzten Commit: Jeder Push auf einen PR, der `src/ai/` oder `eval/` ändert, startet die Auswertung neu, auch wenn er nur `CLAUDE.md` ändert.
- `npm run compare` vergleicht ein Modell an echten Pull Requests (#80, `OPENAI_API_KEY`, `GITHUB_TOKEN` und `COMPARE_MODEL` in der Umgebung, optional `COMPARE_RUNS` 1 bis 5, Standard 3, und `COMPARE_CASES` für eine andere Fallliste): `eval/compare/compare.mjs` ruft für jeden Fall aus `eval/compare/prs.json` `run()` aus `src/main.js` auf einem fremden, gemergten Pull Request auf und gibt Kennzahlen und Findings im Log aus. Es kostet Geld und gehört nicht zu `npm test`; `.github/workflows/compare.yml` startet es nur von Hand mit den Inputs `model`, `runs` und `cases` (`prs` oder `false-alarms`, Standard `prs`; der Workflow bildet daraus über `env` den Pfad `eval/compare/<cases>.json` für `COMPARE_CASES`).
- `npm run build` leert `dist/` und bündelt `src/index.js` mit `@vercel/ncc` neu dorthin: `index.js`, weitere nummerierte `.js`-Dateien für spät geladene Teile, `package.json` und `licenses.txt`. Alle Dateien in `dist/` werden eingecheckt. `test/dist.test.js` startet das eingecheckte Bundle, also erst bauen, dann testen.

Die CI (`.github/workflows/ci.yml`) führt bei jedem Pull Request und bei jedem Push auf `main` `npm ci`, Lint, Tests und Build aus. Sie wird rot, wenn der Build `dist/` verändert, das eingecheckte Bundle also nicht zum Quellcode passt. `test/workflow.test.js` prüft die Regeln für alle Workflow-Dateien.

## Werkzeuge

- Der GitHub-Zugriff läuft über die GitHub CLI (`gh`). Ist sie nicht angemeldet (`gh auth status`), um `gh auth login` bitten, statt einen anderen Weg zu suchen.
- Texte für Git und GitHub (Commit-Messages, PR-Beschreibungen, Kommentare) als UTF-8-Datei übergeben: `git commit -F <datei>`, `gh … --body-file <datei>`. Als Shell-Argument gehen unter Windows Umlaute und Zeilenumbrüche kaputt.
- `gh … --jq`-Ausdrücke mit Anführungszeichen in der Bash ausführen. PowerShell entfernt die inneren Anführungszeichen, und der Ausdruck wird ungültig.
