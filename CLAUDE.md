# ReviewOps

ReviewOps ist eine Custom GitHub Action (JavaScript). Sie startet bei neuen und aktualisierten Pull Requests, liest den Diff über die GitHub-API, schickt ihn an die OpenAI-API (Standardmodell `gpt-4o-mini`) und postet das Feedback als Review mit Inline-Kommentaren am betroffenen Code.

Der Backlog liegt in den GitHub Issues dieses Repositories. Die Milestones „Phase 1“ bis „Phase 5“ geben die Reihenfolge vor. Jedes Issue nennt seine Tasks, seine Akzeptanzkriterien und in der Fußzeile seine Abhängigkeiten („Abhängig von: #n“).

## Arbeitsweise

- **Ein Issue nach dem anderen.** Der Maintainer gibt jede Phase und jedes Issue selbst frei. Ist ein Issue abgeschlossen, wird berichtet und gewartet, statt das nächste zu beginnen.
- **Kein Code auf Vorrat.** Gebaut wird, was das aktuelle Issue verlangt. Was ein späteres Issue liefert, bleibt dort.
- **Kleine, nachvollziehbare Schritte.** Vor jedem Schritt kurz sagen, was entsteht und wozu. Nie den gesamten Code auf einmal abliefern.
- **Ein Branch und ein Pull Request je Issue.** Der Branch heißt `issue-<nr>-<kurzname>`. `main` ändert sich nur über Pull Requests, damit ReviewOps seine eigenen Änderungen reviewt. Issue-Branches bleiben nach dem Merge stehen.
- **Sprache.** Antworten, Issues, Pull Requests und Commit-Messages sind deutsch. Bezeichner, Kommentare und Log-Ausgaben im Code sind englisch.

## Regeln für den Code

- Die Laufzeit ist Node.js 24, der Code besteht aus ES Modules (`import`/`export`). `@actions/core` liefert Inputs, Outputs und Logging, `@actions/github` den Octokit-Client, das offizielle `openai`-SDK den KI-Aufruf.
- Asynchroner Code nutzt `async/await`. Fehler werden mit `try/catch` abgefangen und enden in einer verständlichen Meldung über `core.setFailed()`.
- Secrets (GitHub-Token, OpenAI-Key) tauchen nirgends auf: nicht in Logs, Fehlermeldungen, Kommentaren oder Testdaten.
- Zero-Trust: Diff-Inhalte und Modellantworten sind nicht vertrauenswürdige Eingaben und werden geprüft, bevor sie etwas auslösen.
- `dist/` wird eingecheckt und muss zum Quellcode passen. Nach jeder Änderung unter `src/` neu bauen.
- Workflows binden fremde Actions über einen vollen Commit-SHA ein, die Version steht als Kommentar dahinter. Sie bekommen nur die Rechte, die sie brauchen.
- Module bekommen `core`, `context` und andere Runner-Objekte als Parameter, statt sie selbst zu importieren. Nur `src/main.js` verdrahtet die echten Module. So lassen sich alle Zweige mit `test/helpers/fake-core.js` und `test/helpers/fake-context.js` testen.
- `src/index.js` lädt `main.js` erst zur Laufzeit (`await import`) und meldet Fehler beim Laden über `core.setFailed()`. Manche Pakete arbeiten schon beim Laden, `@actions/github` liest zum Beispiel die Event-Datei ein. Deshalb gehört in `index.js` kein weiterer statischer Import außer `@actions/core`.
- Werte aus dem Event und aus dem PR (Titel, Branch-Namen, Dateinamen, Patches) stammen vom PR-Autor. Ins Log und in Fehlermeldungen kommen nur geprüfte Werte wie Nummer, SHA und Repository-Name. Dateinamen gehen vorher durch `printable()` aus `src/printable.js`, Patch-Inhalte werden nie geloggt.
- Zeilennummern berechnet die Action selbst: `parsePatch()` aus `src/diff/parse.js` liefert je Datei die Hunks und `commentableLines`, die Nummern der hinzugefügten Zeilen. Nur diese Zeilen sind Kommentarziele. Eine Zeilennummer aus einer Modellantwort gilt erst, wenn sie in `commentableLines` steht. `annotateDiff()` aus `src/diff/annotate.js` erzeugt den Diff-Text für das Modell und zeigt Nummern nur an hinzugefügten Zeilen.
- Dateien, die Secrets enthalten können, gehen nie ans Modell: `SENSITIVE_FILES` und `isSensitiveFile()` aus `src/exclude.js` (`.env*`, Schlüssel- und Zertifikatsdateien, `id_rsa*` und Verwandte, `.npmrc`, `.pypirc`, `.netrc`, `.git-credentials`, `credentials.json`, `secrets.*`). Die Liste ist fest, wird vor allen anderen Filtern geprüft und lässt sich über keinen Input ändern. Geprüft werden der neue und bei Umbenennungen auch der alte Name (`previousPath` aus `src/github/files.js`). Solche Dateien stehen mit Grund im Log und in einer Warnung. Erweiterungen der Liste brauchen ein Issue.
- Was wie ein Secret aussieht, maskiert `maskSecrets()` aus `src/secrets.js` direkt nach dem Parsen zu `[REDACTED SECRET]` (`SECRET_PLACEHOLDER`): Private-Key-Blöcke und feste Token-Formate (GitHub, OpenAI, AWS-Access-Key-IDs, Slack, Stripe-Live, Google-API). Ein Schlüsselblock ohne END im Hunk setzt sich im nächsten Hunk fort, solange dessen Zeilen wie der Rest eines Schlüssels aussehen; zwei oder mehr aufeinanderfolgende Zeilen wie ein PEM-Körper (nur Base64, 60 bis 76 Zeichen) werden auch ohne BEGIN und END maskiert, weil ein PR mit einer geänderten Zeile mitten im Schlüssel nur Körperzeilen zeigt. Allgemeine Muster wie `password = "…"` gehören absichtlich nicht dazu, sie träfen Tests und Beispiele. Die regulären Ausdrücke laufen linear, auch bei sehr langen Zeilen vom PR-Autor. Zeilenzahl und Zeilennummern bleiben gleich, alle Zeilenarten werden maskiert, das Budget zählt den maskierten Text. Ins Log kommen nur Anzahl und Dateinamen, nie ein gefundener Wert. Die Auswertung maskiert genauso.
- Welche Dateien nicht reviewt werden, entscheidet `createExcludeFilter()` aus `src/exclude.js`: die Standardliste `DEFAULT_EXCLUDES` plus die Muster aus dem Input `exclude`. Der Abgleich läuft über `picomatch` mit festen Optionen. Eigene Muster sind begrenzt (höchstens zwei `*` und zwei `**` im ganzen Muster, 50 Muster, keine Negation, keine Klammern), weil Dateinamen vom PR-Autor stammen und ein Muster mit vielen Platzhaltern sonst minutenlang rechnet. Gezählt wird über das ganze Muster, weil sich Sterne in mehreren Verzeichnissen multiplizieren. Ein Verzeichnismuster wie `dist/**` meint die Dateien darunter, nicht eine Datei mit dem Namen `dist`. Ein ungültiges Muster lässt den Lauf vor dem ersten API-Aufruf scheitern.
- Der Ablauf in `run()` ist: abrufen, filtern, parsen, begrenzen, bündeln, senden. Bleibt nach dem Begrenzen keine Datei, endet der Lauf grün mit einer `core.notice()`. Alles, was Geld kostet oder etwas postet (KI-Aufruf, Review), steht hinter dieser Stelle.
- Die Größe eines Pull Requests begrenzen `max-files` (Standard 50) und `max-diff-chars` (Standard 200000): `parseLimits()` und `applyLimits()` aus `src/limits.js`. `parseLimits()` liest auch `max-comments`. Gezählt werden die Zeichen des annotierten Diffs, also des Textes, der ans Modell geht. Gewählt wird in der Reihenfolge von GitHub. Eine Datei, die nicht mehr ins Restbudget passt, entfällt allein, spätere kleinere kommen noch hinein. Ausgelassene Dateien stehen mit Grund im Log und in einer Warnung, ein ungültiger Wert scheitert vor dem ersten API-Aufruf. Die Standardwerte stehen in `action.yml` und in `src/limits.js`, ein Test hält sie gleich. Wer den Text für das Modell braucht, nimmt `annotated` der gewählten Datei, statt `annotateDiff()` erneut aufzurufen.
- Den Aufruf des Modells kapselt `createAiClient()` aus `src/ai/client.js` (`complete({ system, user })`), das offizielle `openai`-SDK über die Chat-Completions-Schnittstelle. Die SDK-Optionen sind fest: Adresse `https://api.openai.com/v1`, keine Organisation, kein Projekt, SDK-Logging aus. Ohne sie übernähme das SDK `OPENAI_BASE_URL`, `OPENAI_ORG_ID` und `OPENAI_LOG` aus der Umgebung und schickte Key und Code dorthin. Timeout 120 Sekunden je Versuch, zwei Wiederholungen durch das SDK. Mehrere Aufrufe gleichzeitig sind erlaubt. Der API-Key muss aus sichtbaren ASCII-Zeichen bestehen (`assertInputs()`), sonst scheitert das SDK mit einer Meldung über einen Header.
- Prompt und Antwort des Modells enthalten Code aus dem Diff und werden nie geloggt, auch nicht im Debug-Log. Ins Log kommen nur Kennzahlen: Modell, Token-Verbrauch, Anfrage-ID.
- Fehler des Clients sind `AiError` mit eigenem Text und einem Feld `kind`. Der Text von OpenAI wird nie übernommen und nicht als `cause` angehängt: OpenAI nennt in der Meldung zu einem ungültigen Key dessen Anfang und Ende, und der Schwärzer kennt nur den ganzen Key. Werte aus der Antwort (Code, Typ, Anfrage-ID, Modellname) erscheinen im Log nur, wenn sie wie ein Bezeichner aussehen, die Token-Zahlen nur, wenn alle drei ganze Zahlen ab 0 sind. Nach `auth`, `permission`, `model` und `quota` lohnt kein weiterer Aufruf: `isFatal()` aus `src/ai/error.js`.
- Der Modellname kommt über `parseModel()` aus `src/ai/model.js`. Die Datei importiert das SDK nicht.
- Das Antwortformat des Modells steht an genau einer Stelle: `src/ai/schema.js` (`REVIEW_SCHEMA`, `REVIEW_FORMAT`, `MAX_OUTPUT_TOKENS`, `parseReview()`). Die Anfrage sendet es als Structured Output (`json_schema`, `strict: true`, `max_completion_tokens: 4096`), `parseReview()` prüft die Antwort mit `src/ai/json-schema.js` gegen dasselbe Objekt, auch wenn der Strict-Modus es schon erzwingt. Das Schema hält die Regeln des Strict-Modus ein (alle Felder in `required`, `additionalProperties: false`, keine Längen- und Mengengrenzen); `json-schema.js` kennt nur diesen Teil von JSON Schema und lehnt jedes andere Schlüsselwort ab. Die Tabelle in `docs/response-format.md` und das Schema bleiben gleich, ein Test prüft das. Eine abgeschnittene (`truncated`), gefilterte (`filtered`), abgelehnte (`refusal`) oder nicht passende (`response`) Antwort ist ein Fehler und nie „keine Findings“. Fehlermeldungen nennen nur die Stelle (`findings[2].severity`), nie Inhalt, auch nicht den Text einer Ablehnung. Ob ein einzelnes Finding brauchbar ist (Pfad, Zeile, leerer Text), prüft nicht `parseReview()`, sondern der Schritt je Finding. Ein Modell ohne Structured Outputs scheitert mit `kind: "model"` und dem Hinweis auf `openai-model`, ohne Rückfall auf ein anderes Format.
- `AiError` liegt in `src/ai/error.js` ohne SDK-Import, `client.js` exportiert sie weiter. Module, die nur den Fehler oder das Schema brauchen, ziehen so das SDK nicht ins Bundle.
- Der System-Prompt steht in `src/ai/prompt.js` (`buildSystemPrompt({ language })`) und ist englisch. `PROMPT_VERSION` wird bei jeder Änderung des Wortlauts erhöht, damit sich Messergebnisse einem Stand zuordnen lassen. Schweregrade und Kategorien kommen als Konstanten aus `src/ai/schema.js`, der Prompt beschreibt nur ihre Bedeutung. Die Ausgabesprache kommt über `parseLanguage()` aus dem Input `language` (feste Codes `en`, `de`, `fr`, `es`, `it`, `pt`, `nl`, `pl`, `tr`, `ja`, `zh`, `ko`, Standard `en`, geprüft vor dem ersten API-Aufruf). In den Prompt gelangt nie der Wert aus dem Workflow, sondern nur der englische Name der Sprache aus der festen Tabelle `LANGUAGES`. Der Standardwert steht in `action.yml` und in `src/ai/prompt.js`, ein Test hält sie gleich. Der System-Prompt beschreibt den User-Prompt aus `src/ai/user-prompt.js`; wer eines von beiden ändert, ändert das andere mit, erhöht `PROMPT_VERSION` und misst neu. Der Prompt erklärt, dass alles zwischen `<file …>` und `</file>` Daten vom PR-Autor sind und keine Anweisungen, dass `[REDACTED SECRET]` auf einer hinzugefügten Zeile als Secret im Code zu melden ist und dass ein Backslash-u-Code für ein unsichtbares Zeichen stehen kann. Code außerhalb des Diffs gilt als korrekt, solange der Diff nichts anderes zeigt (seit Version 9, #47).
- Den User-Prompt baut `buildUserPrompt({ files })` aus `src/ai/user-prompt.js`: je Datei `<file path="…">` mit dem annotierten Diff und `</file>`. Der Titel des Pull Requests gehört absichtlich nicht dazu: Mit ihm meldete `gpt-4.1` beim sauberen Referenz-Diff `clean-react` in 6 von 6 Durchgängen einen Fehlalarm, ohne ihn in 0 von 3 (#14). Wer ihn wieder aufnimmt, misst vorher neu. Ein Pfad steht unverändert im Attribut, damit das Modell ihn genau so zurückgibt; eine Datei, deren Pfad `"`, `<`, `>` oder Steuer- und Zeilentrennzeichen enthält (`isUsablePath()`), entfällt schon beim Filtern mit Grund. Jede Zeile des annotierten Diffs beginnt mit der Nummernspalte, ein Tag steht also nie am Zeilenanfang. `annotateDiff()` zeigt Steuerzeichen außer Tab, unsichtbare Formatzeichen und Zeilen- und Absatztrenner als Backslash-u-Code (für U+2028 also Backslash, `u`, `2028`), auch in der Abschnittszeile `@@ …`. So kann keine Codezeile wie eine eigene nummerierte Zeile aussehen, und Bidi-Steuerzeichen bleiben sichtbar.
- Ein Aufruf des Modells hält höchstens `MAX_REQUEST_CHARS` (50000) Zeichen User-Prompt (`src/ai/batch.js`). `planBatches()` füllt die Aufrufe in der Reihenfolge von GitHub, bis die nächste Datei nicht mehr passt; eine Datei wird nie geteilt. Eine Datei, die allein größer ist als ein Aufruf, entfällt schon in `applyLimits()` (`tooLarge`) mit Grund und Warnung und zählt weder für `max-files` noch für `max-diff-chars`.
- `reviewInBatches()` aus `src/review.js` schickt die Aufrufe mit höchstens `MAX_PARALLEL_REQUESTS` (4) gleichzeitig, prüft jede Antwort mit `parseReview()` und liefert je erfolgreichem Aufruf dessen Dateien, Zusammenfassung und Findings (`reviews: { files, summary, findings }[]`) in der Reihenfolge der Aufrufe. Ein fehlgeschlagener Aufruf (`AiError`) nimmt die anderen nicht mit; nach einem fatalen Fehler startet kein neuer, und die nicht gesendeten zählen als fehlgeschlagen. Alles andere als ein `AiError` ist ein Defekt und lässt den Lauf scheitern. In `run()` gilt: Schlägt ein Teil fehl, endet der Lauf grün mit einer Warnung (Zahl der Aufrufe und Dateien, Meldungen des Clients) und je einer Zeile „Not reviewed …“; schlagen alle fehl, scheitert er mit der Meldung des ersten Fehlers. Ins Log kommen nur Zahlen: Dateien und Aufrufe, Findings je Schweregrad. Findings werden bis #17 nicht gepostet.
- Jeder Text der Modellantwort wird in `reviewInBatches()` direkt nach `parseReview()` durch `boundReview()` aus `src/ai/answer-limits.js` begrenzt und bereinigt (`TEXT_LIMITS`: Titel 150, Kommentar 1500, Vorschlag 1500, Zusammenfassung 1000 Zeichen, nach Zeichen gezählt, gekürzt mit `…`; Steuerzeichen, unsichtbare Formatzeichen und leer aussehende Zeichen wie das Braille-Leerzeichen entfallen, der Titel wird einzeilig). Alles dahinter sieht nur diese Texte. Das Ergebnis nennt die Zahl der gekürzten Texte als `shortened`. Markdown entschärft erst das Review selbst.
- Fehlt der API-Key, entscheidet `explainMissingSecret()` aus `src/github/context.js`: Bei einem Fork-PR oder einem von Dependabot ausgelösten Lauf (`context.actor`) hat GitHub keine Secrets bereitgestellt, und `run()` endet vor jeder Anfrage grün mit einer `core.notice()`. Bei jedem anderen PR bleibt es ein Fehler. Der Text der Meldung enthält nichts aus dem Event.
- `SECURITY.md` beschreibt Datenfluss, Rechte, Events, Umgang mit der Antwort und den Meldeweg. `test/security-doc.test.js` hält Sperrliste, Rechte und Textgrenzen darin mit dem Code gleich und sichert `src/`: kein `eval`, keine Funktionen aus Text, kein `child_process`, kein eigener Netzaufruf, nur die vier erlaubten Pakete (`@actions/core`, `@actions/github`, `openai`, `picomatch`), ein neues Paket ist eine Entscheidung des Maintainers. Wer das Verhalten der Action ändert, ändert `SECURITY.md` mit.
- Welche Findings das Review zeigt, entscheidet `selectFindings()` aus `src/findings.js`, eine reine Funktion, je Finding gegen die Dateien des eigenen Aufrufs: Ein leerer Titel, Kommentar oder Vorschlag (nur Leer- oder Formatzeichen) und ein Pfad, der nicht exakt zu einer Datei dieses Aufrufs gehört, fallen weg; ein unbekannter Pfad kommt auch nicht in den Review-Text, weil das Modell die Datei nie gesehen hat. Von Findings mit gleichem Pfad, gleicher Zeile und gleichem Titel (ohne Groß- und Kleinschreibung und überzähligen Leerraum) bleibt das schwerste. Danach wird stabil nach Schweregrad sortiert und auf `max-comments` gekürzt (Standard 10, in `action.yml` und `src/limits.js`, gelesen von `parseLimits()`). Die Grenze gilt für alle gezeigten Findings, der Rest entfällt und wird gezählt. Erst dann wird aufgeteilt: Steht die Zeile in `commentableLines`, wird das Finding ein Inline-Kommentar (`inline`), sonst steht es im Review-Text (`unplaced`). Ins Log kommt eine Zeile mit den Zahlen jedes Schritts, nie ein Pfad oder Text eines Findings. Die Tabelle in `docs/response-format.md` beschreibt die Schritte.
- Ein Aufruf kann drei Versuche zu 120 Sekunden dauern, ein Pull Request der Standardgröße braucht höchstens etwa acht Aufrufe, also zwei Runden zu vier. Deshalb hat der Job in `reviewops.yml` `timeout-minutes: 15`; `test/workflow.test.js` rechnet das nach.
- Die Auswertung des Prompts liegt unter `eval/` und gehört nicht zu `src/` und nicht ins Bundle. `eval/cases/*.json` sind die Referenz-Diffs (je ein Fehler pro Fokusbereich, `security-prompt-injection` mit einer eingebetteten Anweisung an die KI und zwei saubere; den User-Prompt baut `buildUserPrompt()` wie in der Action), `eval/lib.mjs` enthält die Bewertung ohne API-Aufruf und ist Teil von `npm test`, `eval/run.mjs` ruft die echte API auf. Ein Lauf, der mit einem Fehler endet (abgeschnitten, gefiltert, abgelehnt, Netz), zählt nie als bestanden, auch nicht bei einem sauberen Diff. Die Auswertung sendet höchstens zwei Aufrufe gleichzeitig (`MAX_PARALLEL_EVAL_REQUESTS`) und wartet nach `rate_limit` bis zu zweimal 20 Sekunden, bevor sie es erneut versucht; mit vier gleichzeitig überschritt sie das Token-Limit pro Minute von `gpt-4.1` auf dem Konto des Projekts (#15, #47). Ein `rate_limit`, das danach bleibt, ist ein Fehler des Laufs. Nur die Auswertung darf Findings des Modells ausgeben, weil es um die eigenen Testdaten geht, und auch dort nur durch `printable()` und mit einem festen Zeichen vor jeder Zeile (`> ` oder `- `): Der Runner entfernt führende Leerzeichen, bevor er eine Zeile als Workflow-Befehl (`::error::`) liest, Einrückung schützt also nicht. Die Auswertung gibt je Fehlerfall ein Beispiel-Finding mit seinem Vorschlag aus. Für die Action gilt weiter: Prompt und Antwort werden nie geloggt.
- Inputs, die Zugangsdaten sind, nennt `secretsOf()` aus `src/inputs.js`. Nur sie werden maskiert und geschwärzt. Einstellungen wie `exclude` erscheinen im Log.
- Ein Patch, den `parsePatch()` nicht lesen kann, lässt den Lauf nicht scheitern. Die Datei wird mit Grund übersprungen, und die Meldung nennt nur die Stelle im Patch, nie dessen Inhalt.
- Tests rufen nie die echte GitHub-API auf. Unit-Tests nutzen `createFakeOctokit()`, alles andere den lokalen Testserver `startGitHubApi()` aus `test/helpers/github-api.js`. Prozess-Tests zeigen ohne eigene Angabe auf eine tote lokale Adresse. Auch OpenAI wird nie erreicht: Die Adresse ist in der Action fest, deshalb lädt `startAction()` per `--import` `test/helpers/redirect-openai.js`, das Anfragen an `https://api.openai.com/v1` auf `TEST_OPENAI_URL` umleitet (den lokalen Ersatz `startOpenAiApi()` aus `test/helpers/openai-api.js`) oder ohne Angabe auf eine tote Adresse.
- In Quelldateien stehen keine unsichtbaren Zeichen und keine Unicode-Escapes für sie. Sonderzeichen entstehen über `String.fromCodePoint()` oder Unicode-Kategorien wie `\p{Zl}`. `test/source-hygiene.test.js` prüft das.
- Testdaten in der Form echter Secrets (Tokens, Private-Key-Blöcke) entstehen erst zur Laufzeit aus Teilstücken, etwa `` `gh${"p"}_${"Ab1".repeat(12)}` ``. Keine Datei des Repositorys enthält etwas, das wie ein Zugangsdatum aussieht.
- ReviewOps entscheidet nie über einen Merge: Im Quellcode stehen weder `APPROVE` noch `REQUEST_CHANGES`, `test/review-event.test.js` prüft das. Den Review vom Typ `COMMENT` belegt #17.

## Logging

Ausgaben laufen ausschließlich über `@actions/core`; `console.*` ist unter `src/` per ESLint verboten.

- `core.info()` meldet den Fortschritt, eine Zeile je Schritt.
- `core.notice()` ist für Hinweise an den Nutzer der Action, etwa einen übersprungenen Lauf.
- `core.warning()` meldet, was übersprungen oder nur teilweise erledigt wurde, ohne dass der Lauf scheitert.
- `core.debug()` nimmt Details und Stacktraces auf. Sie erscheinen nur bei eingeschaltetem Debug-Logging.
- `core.setFailed()` wird nur in `run()` aufgerufen, mit einer Meldung, die sagt, was zu tun ist.
- Nie ausgegeben werden Payloads, Header und ganze Fehlerobjekte. Fehlertexte gehen vor der Ausgabe durch den Schwärzer aus `src/redact.js`.

## Ablauf je Issue

| Schritt | Skill | Ergebnis |
|---|---|---|
| Standort klären | `/orientation` | Projektstand und nächstes umsetzbares Issue |
| Issue schärfen | `/drilling <nr>` | geklärte Entscheidungen und ein abgestimmter Plan |
| Umsetzen | `/implement <nr>` | Code, Tests und ein Nachweis je Akzeptanzkriterium |
| Prüfen | `/review-issue <nr>` | Befunde und ein Urteil |
| Abschließen | `/ship <nr>` | Commit und Pull Request, nach dem Merge ein abgehaktes Issue |
| Fehler suchen | `/diagnose` | Ursache eines fehlgeschlagenen Workflow-Laufs |

Fehlt beim Aufruf die Issue-Nummer, ergibt sie sich aus dem Branch-Namen. Auf `main` ist das nächste umsetzbare Issue gemeint: das offene Issue mit der kleinsten Nummer im frühesten Milestone mit offenen Issues, dessen Abhängigkeiten alle geschlossen sind. Der Maintainer bestätigt es, bevor gearbeitet wird.

## Befehle

- `npm ci` installiert die Abhängigkeiten exakt nach `package-lock.json`.
- `npm test` führt die Tests mit dem eingebauten Test-Runner aus (`node --test`). Testdateien liegen unter `test/` und heißen `*.test.js`.
- `npm run lint` prüft den Code mit ESLint und die Formatierung mit Prettier.
- `npm run format` formatiert den Code mit Prettier (Standardstil, Markdown ausgenommen).
- `npm run eval` wertet den Prompt gegen die echte OpenAI-API aus (`OPENAI_API_KEY` in der Umgebung, optional `EVAL_MODEL` und `EVAL_LANGUAGE`): jeder Referenz-Diff dreimal, ohne `EVAL_LANGUAGE` auf Englisch, Ergebnis als Tabelle. `EVAL_LANGUAGE` prüft `parseLanguage()` wie den Input `language` der Action; die Schwellen gelten in jeder Sprache, weil Schweregrad, Kategorie, Pfad und Zeile englisch bleiben. Gemessen wird mit dem Referenzmodell `gpt-4.1` (`REFERENCE_MODEL` in `eval/lib.mjs`), nicht mit dem Standardmodell der Action. Mit `gpt-4o-mini` erreicht der Prompt nicht alle Schwellen, es findet den N+1-Fall nicht; welches Modell Standard wird, entscheidet #41. Die Schwellen: ein Fehlerfall wird in 3 von 3 Läufen gefunden, ein sauberer Diff bleibt in mindestens 2 von 3 Läufen ohne Finding ab `major` (das weicht vom Wortlaut „3 von 3“ in #12 ab), ungültige Findings sind nie erlaubt, und ein Lauf mit Fehler wird nie toleriert. Begründung der Schwellen (#47): Die Fehlerfälle fand `gpt-4.1` in den Läufen aus #12 jedes Mal (3 von 3), deshalb gilt dort 3 von 3. Geschwankt haben nur die sauberen Diffs: Dasselbe Modell mit demselben Prompt war in #12 einmal grün und einmal rot. Der wiederkehrende Fehlalarm bei `clean-react` kam vom PR-Titel im Prompt (6 von 6 Durchgängen mit Titel, 0 von 3 ohne, #14). Mit Prompt-Version 8 waren in #47 sechs Läufe auf unverändertem Stand fünfmal grün und einmal rot: Die Fehlerfälle wurden immer gefunden, `clean-csharp` blieb immer sauber, `clean-react` hatte 3 Fehlalarme in 18 Durchgängen, die alle über Code außerhalb des Diffs rieten (ob eine Prop stabil ist, ob ein `AbortSignal` beachtet wird); ein Lauf auf Deutsch erfüllte alle Schwellen. Version 9 macht die Regel „nicht raten“ deshalb an solchen Beispielen konkret; danach waren fünf Läufe auf unverändertem Stand alle grün, mit jedem Fall in jedem Lauf bei 3 von 3, auch `clean-react` (15 von 15), und ebenso der Lauf auf Deutsch. Die Toleranz von einem Ausreißer bleibt, damit ein einzelner Fehlalarm bei unverändertem Prompt den Check nicht rot färbt. Mehr Läufe je Fall kosten zwei Drittel mehr und drücken auf das Token-Limit von `gpt-4.1`; ein automatischer Sprachtest brächte neue Streuung. Ob das Feedback in der gewählten Sprache kommt, belegt ein Lauf von Hand mit `language` (#47). Er endet mit Fehler, wenn eine Schwelle verfehlt wird oder der Key fehlt. Nur bei einem Pull Request ohne Secrets (Fork) endet er ohne Key mit einem Hinweis. Er gehört nicht zu `npm test`; `.github/workflows/eval.yml` startet ihn bei Änderungen an `src/ai/`, `eval/` und am Workflow sowie von Hand, dann mit den Inputs `model` und `language`. Läufe von Hand auf demselben Branch teilen sich eine Concurrency-Gruppe und brechen einander ab; für Messreihen werden sie nacheinander gestartet. Der Pfadfilter betrachtet den ganzen Pull Request, nicht nur den letzten Commit: Jeder Push auf einen PR, der `src/ai/` oder `eval/` ändert, startet die Auswertung neu, auch wenn er nur `CLAUDE.md` ändert.
- `npm run build` leert `dist/` und bündelt `src/index.js` mit `@vercel/ncc` neu dorthin: `index.js`, weitere nummerierte `.js`-Dateien für spät geladene Teile, `package.json` und `licenses.txt`. Alle Dateien in `dist/` werden eingecheckt. `test/dist.test.js` startet das eingecheckte Bundle, also erst bauen, dann testen.

Die CI (`.github/workflows/ci.yml`) führt bei jedem Pull Request und bei jedem Push auf `main` `npm ci`, Lint, Tests und Build aus. Sie wird rot, wenn der Build `dist/` verändert, das eingecheckte Bundle also nicht zum Quellcode passt. `test/workflow.test.js` prüft die Regeln für alle Workflow-Dateien.

## Werkzeuge

- Der GitHub-Zugriff läuft über die GitHub CLI (`gh`). Ist sie nicht angemeldet (`gh auth status`), um `gh auth login` bitten, statt einen anderen Weg zu suchen.
- Texte für Git und GitHub (Commit-Messages, PR-Beschreibungen, Kommentare) als UTF-8-Datei übergeben: `git commit -F <datei>`, `gh … --body-file <datei>`. Als Shell-Argument gehen unter Windows Umlaute und Zeilenumbrüche kaputt.
- `gh … --jq`-Ausdrücke mit Anführungszeichen in der Bash ausführen. PowerShell entfernt die inneren Anführungszeichen, und der Ausdruck wird ungültig.
